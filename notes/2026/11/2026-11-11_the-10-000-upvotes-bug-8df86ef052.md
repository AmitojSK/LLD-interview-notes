How do you prevent double voting?

## Problem understanding

The problem involves designing a system to prevent double voting, specifically in a scenario like an upvote/downvote mechanism commonly found in social media, forums, or Q&A platforms. The key constraints and goals include:

- **Uniqueness of votes**: Each user can only upvote or downvote a particular item (post, comment, etc.) once.
- **Consistency and correctness**: The vote count must reflect the true number of unique votes.
- **Scalability**: The system should handle a large number of users and votes without degradation.
- **Performance**: Vote recording should be fast and concurrently safe.
- **Concurrency**: Multiple votes may come in simultaneously for the same item or user.
- **Idempotency**: Repeated requests from the same user to vote on the same item do not cause multiple votes.

## Interview answer

To prevent double voting, we need a design that guarantees each user votes only once per item. The core idea is to maintain a mapping between users and their votes on items. Key approaches:

1. **Data storage design:**
   - Use a database table that stores (user_id, item_id, vote_type) tuples.
   - Enforce uniqueness constraint on (user_id, item_id) to prevent duplicates.
   - The vote_type field can be `upvote`, `downvote`, or `none` (for vote removal).

2. **Process flow:**
   - When a user attempts to vote, check if a record for (user_id, item_id) exists.
   - If none, create a new vote record.
   - If it exists and the vote_type differs, update the vote.
   - If the vote_type is the same, ignore or return idempotent success.

3. **Concurrency and atomicity:**
   - Use database transactions to ensure atomic check-and-insert/update.
   - To handle concurrency, rely on database constraints (unique indexes) and possibly optimistic locking.
   - In highly concurrent systems, consider using a distributed lock or conditional update strategies like Compare-And-Set.

4. **Caching and bloom filters:**
   - For performance, cache vote states or use in-memory stores (e.g., Redis) to quickly detect double votes.
   - Use bloom filters to prevent invalid repeat votes but always validate against the persistent store on write.

5. **Edge cases:**
   - Removing votes (changing an upvote to none).
   - Voting multiple times rapidly or from different devices.
   - Handling data consistency if distributed databases or eventual consistency architectures are used.

6. **Trade-offs:**
   - Strong consistency vs. performance: database constraints are reliable but can create transaction bottlenecks.
   - Caching reduces latency but risks stale data or false positives.
   - Complexity of distributed locks may not be worth it for smaller-scale deployments.

## Java implementation

Here's a simplified Java backend design illustrating vote recording and prevention of double voting. Assume a relational database and JPA for persistence.

```java
import javax.persistence.*;
import javax.transaction.Transactional;
import java.util.Optional;

// Enum for vote types
public enum VoteType {
    UPVOTE, DOWNVOTE, NONE
}

// Entity representing a vote
@Entity
@Table(name = "votes", uniqueConstraints = @UniqueConstraint(columnNames = {"userId", "itemId"}))
public class Vote {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private Long userId;
    private Long itemId;

    @Enumerated(EnumType.STRING)
    private VoteType voteType;

    // Constructors, getters, setters omitted for brevity
}

// Vote Repository interface
public interface VoteRepository extends JpaRepository<Vote, Long> {
    Optional<Vote> findByUserIdAndItemId(Long userId, Long itemId);
}

// Vote service to handle vote operations
@Service
public class VoteService {

    private final VoteRepository voteRepository;

    @Autowired
    public VoteService(VoteRepository voteRepository) {
        this.voteRepository = voteRepository;
    }

    /**
     * Records a vote from a user on an item. Returns true if the vote was recorded or changed,
     * false if it was a duplicate vote (same vote type).
     */
    @Transactional
    public boolean vote(Long userId, Long itemId, VoteType newVoteType) {
        Optional<Vote> existingVoteOpt = voteRepository.findByUserIdAndItemId(userId, itemId);

        if (existingVoteOpt.isPresent()) {
            Vote existingVote = existingVoteOpt.get();
            if (existingVote.getVoteType() == newVoteType) {
                // Same vote, idempotent operation - ignore
                return false;
            } else {
                // Vote type changed, update it
                existingVote.setVoteType(newVoteType);
                voteRepository.save(existingVote);
                return true;
            }
        } else {
            // No vote yet, create new
            Vote newVote = new Vote();
            newVote.setUserId(userId);
            newVote.setItemId(itemId);
            newVote.setVoteType(newVoteType);
            voteRepository.save(newVote);
            return true;
        }
    }
}
```

### Explanation

- The unique constraint on (userId, itemId) prevents duplicate votes at the database level.
- The `vote()` method checks if a vote exists; if the same vote, it returns false to indicate no change.
- If different, it updates the vote.
- Transactions ensure atomic operations.
- If two concurrent identical attempts occur, one will fail due to the unique constraint; your application should handle such exceptions gracefully and retry or respond appropriately.

### Failure modes and edge cases

- Race conditions in vote creation can be controlled by retries on unique constraint violations.
- Long-running transactions should be avoided.
- If scaling horizontally, consider using Redis or distributed counters but always reconcile with the database.

## Key follow-up questions

1. **Q: How would you handle concurrent votes to prevent race conditions?**  
   **A:** Use database transactions with unique constraints. Attempt insert, catch unique constraint violation exceptions, then retry or update. Alternatively, optimistic locking/versioning ensures concurrent updates are detected.

2. **Q: What if a user tries to vote multiple times quickly?**  
   **A:** The system should treat repeated votes with the same value as idempotent no-ops. The database constraint and application logic prevent multiple records.

3. **Q: How do you scale this voting system for millions of votes?**  
   **A:** Use sharding or partitioning of votes by item to distribute load. Employ caching layers (Redis) for fast read and delayed writes with eventual consistency. Also consider queueing vote requests for batch processing.

4. **Q: Can vote removal be supported?**  
   **A:** Yes, by setting the vote type to `NONE` or deleting the vote record. The service method can handle these cases explicitly.

5. **Q: What happens if the voting data store goes down?**  
   **A:** Implement retries and fallback mechanisms. Consider using a write-ahead log or queue to capture votes for retry later to avoid data loss.

- Edge cases such as vote changes/removals and concurrent requests must be accounted for.
